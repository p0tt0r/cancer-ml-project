# CLAUDE.md — cancer-ml-project

## О проекте

Учебный проект по машинному обучению на онкологических данных. Цель — научиться самостоятельно строить модели, которые работают с данными раковых больных и считают разные показатели (диагноз, риск, прогноз).

Главное правило: **я учусь, а не собираю код**. Мне важно понимать логику каждой строки, каждой библиотеки и каждого шага подготовки данных, чтобы потом самому оценивать задачи и выбирать шаги, а AI использовать уже как ускоритель.

## План

1. **Проект 1 — классификация опухолей** (Breast Cancer Wisconsin, встроен в sklearn). Готово: `breast_cancer_classification_cleanData.ipynb`.
   - EDA, train/test split со `stratify`, `StandardScaler` без утечки данных, `LogisticRegression`, метрики, confusion matrix, подбор порога классификации.
2. **Проект 2 — «грязные» реальные данные.** Следующий шаг. Планируемый датасет: Cervical Cancer Risk Classification (Kaggle). Темы: пропуски (MCAR / MNAR, импутация, флаг пропуска), категориальные признаки (label / one-hot, `drop_first`), Random Forest / Gradient Boosting, кросс-валидация.
3. **Проект 3 — survival-анализ** (прогноз времени выживания, библиотека `lifelines`).
4. **Исследовательский проект** — сам формулирую гипотезу, выбираю датасет, сравниваю модели, интерпретирую признаки.
5. **ML Engineering** — встраиваю модель из п. 4 в продукт (API, интерфейс, мониторинг).

## Важные детали данных (проект 1)

- В Breast Cancer Wisconsin **0 = malignant, 1 = benign**. Порядок неинтуитивный, легко перепутать.
- `predict_proba(...)[:, 1]` — вероятность **benign**. Чтобы реже пропускать malignant, порог для benign нужно **повышать**, а не понижать.
- Ключевая метрика — **recall для malignant** (пропущенный рак дороже ложной тревоги). Для неё в sklearn нужен `pos_label=0`.

## Как со мной работать

- **Формат объяснения:** что это → зачем нужно → как работает → пример → что делать конкретно.
- Перед кодом — короткая теория: почему именно этот метод, что происходит математически. Не просто «подключи библиотеку».

- **Отладка:** одна наиболее вероятная причина за раз (проверить → результат → следующая), а не список из многих причин. Команды давать конкретно и объяснять, зачем их выполнять.
